# Архитектурный дизайн: сбор отчётов об итогах обсуждения (Этап 2, `Report`)

Дата: 2026-09-23

## Контекст

Продуктовое ТЗ (`docs/superpowers/specs/2026-09-20-analytics-product-requirements.md`,
раздел 27, Этап 2) относит расширение сборщика на `Report[]` к
следующему после `Document[]`/`DocumentVersion` шагу. Раздел 6.3
продуктового ТЗ описывает целевые данные как «отчёты о результатах
обсуждения» и «HTML-представление отчёта, если доступно».

`robots.txt` источника запрещает `/report`. Владелец продукта
(2026-09-23) подтвердил тот же осознанный подход, что уже применён к
`/npa/view` и `/application` — см. `docs/superpowers/specs/2026-09-15-legalacts-scraper-design.md`,
раздел «Осознанное решение по `robots.txt` для `/report` (2026-09-23)».
Там же зафиксированы находки живой проверки, на которых основан этот
дизайн:

- `/report?id=<external_id акта>` — та же карточка, отдельного
  id-пространства нет (в отличие от `/application/viewcardhistory`).
- Ссылка «Посмотреть отчёт» появляется на карточке `/npa/view` только
  когда обсуждение завершено — на активных карточках её нет.
- Таблица отчёта (`Раздел`/`Комментарии`/`Ответ`/`Нравится`/`Не
  нравится`) содержит официальный текстовый ответ государственного
  органа — данные, которых сейчас нет в модели вообще (текущий
  парсер комментариев видит официальный ответ только как безымянный
  вложенный комментарий через `parent_external_comment_id`).
- Надёжной связки строк таблицы с уже собранными `Comment` по id нет
  (сопоставление возможно только по тексту, что хрупко).

## Область действия и решения по объёму

- В этой итерации собирается **только сырой HTML отчёта целиком**, без
  разбора строк таблицы на структурированные пары комментарий/ответ —
  ровно то, что раздел 6.3 продуктового ТЗ и называет минимальным
  требованием («HTML-представление отчёта, если доступно»). Разбор
  строк на связанные с `Comment` записи — отдельная задача на будущее,
  когда будет решено, как надёжно сопоставлять строки с комментариями.
- Отчёт **insert-once**: если запись `Report` для акта уже есть,
  повторный обход не перезапрашивает `/report` для этого акта. Отчёт
  появляется только после завершения обсуждения и не предполагается
  изменяющимся впоследствии.
- Раздел `arv` не проверяется на наличие отчёта — шаблон `.blog-item`
  не даёт таких ссылок в принципе (тот же класс явления, что и с
  вкладками комментариев/версиями для этого раздела).
- `/application/downloadreport?id=<N>` (скачивание файла) — вне
  объёма этой итерации, уже покрыт существующим решением по
  `/application/`, но собирать его сейчас не будем (аналогично
  `conceptFiles`/приложенным файлам версий).

## Схема таблицы

### `reports` (новая)

```text
id                PK (внутренний)
legal_act_id      FK -> legal_acts, unique, not null   -- максимум один отчёт на акт
raw_html_ru       Text, nullable
first_seen_at     DateTime(timezone=True), not null     -- наши часы, UTC
```

Отдельного `external_id` не нужно — отчёт живёт по тому же id, что и
сама карточка акта (`/report?id=<external_id>`), поэтому `legal_act_id`
уже однозначно адресует запись. Никакого снапшот-механизма
(`content_sha256`) не нужно — insert-once по построению, тем же
принципом, что и `DocumentVersion`.

## Изменения в парсере (`backend/scraper/parsers/document_page.py`)

Новая функция `parse_report_link(html) -> str | None`:

```python
def parse_report_link(html):
    soup = BeautifulSoup(html, "lxml")
    link = soup.select_one('a[href^="/report?id="]')
    return link["href"] if link else None
```

Селектор завязан только на префикс URL, не на текст кнопки/CSS-классы
(они могут меняться) — устойчивее, чем текстовое сопоставление.

## Механика сбора (`backend/scraper/run.py`)

В `process_document_entry`, внутри уже существующего блока
`if section != "arv":` (после сбора версий), добавляется:

```text
report_url = parse_report_link(ru_html)
если report_url не None и не report_exists(legal_act_id):
    response = fetcher.get(urljoin(BASE_URL, report_url))
    если response.status_code != 404:
        upsert_report(legal_act_id, response.text, timestamp)
```

Без try/except — сетевой сбой всплывает в `run()` тем же принципом,
что и остальное тело `process_document_entry`.

## Изменения в `store.py`

- `report_exists(session, legal_act_id) -> bool`.
- `upsert_report(session, legal_act_id, raw_html_ru, now)` — простой
  insert, без `_get_or_create` (нет справочных полей), без снапшотов.

## Миграция

Одна новая Alembic-ревизия (`0003`) поверх `0002_document_versions.py`:
создаёт `reports` с `unique(legal_act_id)` FK на `legal_acts`.

## Тестирование

- `test_document_page.py`: `parse_report_link` — есть ссылка / нет
  ссылки.
- `test_store.py`: `report_exists` до/после вставки; `upsert_report`
  сохраняет `raw_html_ru`/`first_seen_at`.
- `test_run.py`: обход сохраняет отчёт, когда ссылка есть; повторный
  обход не делает лишнего запроса, если отчёт уже сохранён; `arv`-документ
  не порождает запросов к `/report`; документ без ссылки на отчёт (обсуждение
  ещё не завершено) не порождает запросов и не падает.

## Критерии приёмки

1. `db/models.py` содержит `Report` с полями и констрейнтами выше;
   новая Alembic-ревизия применяется чисто поверх `0002`.
2. Обход сохраняет `raw_html_ru` отчёта, когда ссылка на карточке
   есть.
3. Повторный обход того же акта не делает лишнего запроса `/report`
   для уже сохранённого отчёта.
4. `arv`-документы и документы без ссылки на отчёт не порождают
   запросов к `/report` и не падают.
5. Полный backend pytest-suite проходит.
