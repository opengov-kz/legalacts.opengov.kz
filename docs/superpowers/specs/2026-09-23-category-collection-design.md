# Архитектурный дизайн: сбор категорий/тематик (Этап 2, `Category`)

Дата: 2026-09-23

## Контекст

Продуктовое ТЗ (`docs/superpowers/specs/2026-09-20-analytics-product-requirements.md`,
раздел 27, Этап 2) относит категории/тематики к списку полей, ещё не
собираемых сборщиком. В отличие от `DocumentVersion` и `Report`,
живая проверка (2026-09-23) показала, что категория — это **не поле
карточки документа**, а фильтр списочных страниц: на `/npa/view`
категория не отображается нигде, кроме скрытой формы расширенного
поиска (`<p>Категория</p>` + `<select id="categoryId">`), которая
присутствует одинаково на любой странице сайта (и на списках, и на
карточках документов) и не зависит от того, какая категория сейчас
выбрана — атрибут `selected` в этом `<select>` не выставляется
никогда, даже на отфильтрованной странице.

Живьём подтверждено:

- `/list?categoryId=N` (раздел `npa`) — тот же движок, что у обычного
  списка; фильтрация подтверждена по числу карточек и `totalPages`.
- `/application/kdrpcp?categoryId=N` — не самостоятельный эндпоинт, а
  редирект-заглушка (HTTP 302) на
  `/list?types[0]=7001&types[1]=7002&categoryId=N&page=0&type=0`.
  Для `kdrp` нужно сразу строить целевой URL `/list`, не дёргая
  заглушку.
- `/Arvlist?categoryId=N` (раздел `arv`) — фильтрация подтверждена:
  без фильтра `totalPages: 63`, для `categoryId=1874` — `totalPages: 3`;
  для `categoryId=15888765` — 0 карточек (пустая категория для этого
  раздела, ожидаемый случай, не ошибка).
- `/application/withdraw?categoryId=N` (раздел `withdraw`) — раздел
  крошечный (1 запись на весь сайт на момент проверки), фильтрацию
  достоверно подтвердить не удалось, но при таком объёме риск
  незначителен.
- Полная таксономия — 24 категории, id и имена подтверждены из
  живого выпадающего списка (от `346: Информационные технологии` до
  `15888768: Организационные вопросы`).

Ссылки на карточки внутри отфильтрованного списка используют тот же
шаблон `div.contentlist > h3 a[href]`, что уже разбирает
`list_page.parse_list_page` — новый парсер карточек не нужен.

## Область действия и решения по объёму

- Категория — это связь **многие-ко-многим** между `LegalAct` и
  `Category`: один акт может входить в несколько категорий, одна
  категория содержит много актов.
- **Если акт, найденный на отфильтрованной странице, ещё не
  обработан сборщиком (нет записи `LegalAct` с таким `external_id`) —
  связь не создаётся, страница просто пропускается.** Решение
  владельца продукта (2026-09-23): не заводить акт как документ через
  обход по категории — полагаемся на то, что акт будет обнаружен
  штатным обходом `list`/`Arvlist`, а связка с категорией
  доберётся повторным обходом (`requeue_stale_lists`, см. ниже).
- Затравка обхода по категориям строится на основе **статического**
  списка `CATEGORIES` (24 пары `id, name`) в `run.py`, аналогично уже
  существующему `SEED_LIST_URLS`. Список используется только для
  построения стартовых URL; фактическое имя `Category.name`,
  сохраняемое в базу, всегда парсится заново с живой страницы (см.
  «Механика сбора») — самовосстанавливается, если сайт переименует
  категорию. Появление 25-й категории на сайте потребует ручного
  добавления в `CATEGORIES`, как и появление нового раздела сейчас
  потребовало бы ручного добавления в `SEED_LIST_URLS`.
- Архивные варианты (`status=IN_ARCHIVE` для `npa`/`arv`) **включены**
  в затравку — решение владельца продукта (2026-09-23): полнота
  данных важнее объёма, обход и так резюмируемый и фоновый.
- Это самая объёмная по трафику фича Этапа 2: не 1-2 доп. запроса на
  документ (как у `DocumentVersion`/`Report`), а 144 новых стартовых
  list-страницы (6 существующих seed-записей × 24 категории), каждая
  со своей пагинацией (от единиц до 100+ страниц по живым замерам).
  Карточки документов при этом не дублируют HTTP-нагрузку на
  `/npa/view` — они дедуплицируются по URL в `crawl_queue`, обходом
  по категориям создаются только сами списочные запросы плюс записи
  связей для уже известных актов.
- Раздел `arv` **не исключается** из обхода по категориям (в отличие
  от расширения комментариев/версий/отчётов) — фильтрация по
  категории для `arv` работает независимо от отсутствия вкладок
  комментариев/версий у этого раздела.

## Схема таблицы

### `categories` (новая)

```text
id                PK (внутренний)
external_id       Integer, unique, not null   -- categoryId сайта
name              Text, not null               -- живое имя с сайта
```

### `legal_act_categories` (новая, join-таблица)

```text
id                PK (внутренний)
legal_act_id      FK -> legal_acts, not null
category_id       FK -> categories, not null
first_seen_at     DateTime(timezone=True), not null   -- наши часы, UTC
unique(legal_act_id, category_id)
```

## Изменения в парсере (`backend/scraper/parsers/list_page.py`)

Новая функция `parse_category_name(html, category_id) -> str | None`:

```python
def parse_category_name(html, category_id):
    soup = BeautifulSoup(html, "lxml")
    option = soup.select_one(f'option[value="{category_id}"]')
    return option.get_text(strip=True) if option else None
```

`category_id` передаётся вызывающим кодом (он же строил URL с этим
`categoryId`) — не нужно искать `selected`, которого в разметке нет.

## Механика сбора (`backend/scraper/run.py`)

Новая константа `CATEGORIES` (24 пары `(external_id, name)`,
зафиксированные живой проверкой 2026-09-23) и вспомогательная функция
для подстановки параметра, по образцу уже существующих
`_set_page_param`/`_with_type_comment`:

```python
def _with_category(url, category_id):
    parts = urlsplit(url)
    query = dict(parse_qsl(parts.query))
    query["categoryId"] = str(category_id)
    return urlunsplit((parts.scheme, parts.netloc, parts.path, urlencode(query), parts.fragment))
```

`seed_queue()` расширяется: помимо существующих `SEED_LIST_URLS`,
для каждой пары (section, url) из `SEED_LIST_URLS` и каждой категории
из `CATEGORIES` добавляется запись `page_type="category_list"` с URL
`_with_category(url, category_id)`.

Новый обработчик `process_category_list_entry(session, fetcher, url, section)`:

```text
response = fetcher.get(url)
если response.status_code == 404: return
category_id = categoryId из query-параметров url
category_name = list_page.parse_category_name(response.text, category_id)
category = store.get_or_create_category(category_id, category_name)

для каждой карточки list_page.parse_list_page(response.text):
    external_id = id из query-параметров карточки
    legal_act_id = store.legal_act_id_for_external_id(external_id)
    если legal_act_id не None:
        store.link_legal_act_category(legal_act_id, category.id)

total_pages = list_page.parse_total_pages(response.text)
если текущая страница < total_pages:
    enqueue следующую страницу того же фильтра, page_type="category_list"
```

Пагинация переиспользует существующие `_current_page`/
`_set_page_param` без изменений — `_set_page_param` уже сохраняет
все параметры запроса, включая `categoryId`, при добавлении `page`.

**Изменение приоритета очереди в `run()`:** третий уровень после
`list` и `document` — `category_list` обрабатывается, только когда
очереди `list` и `document` пусты на данный момент цикла (тот же
паттерн `next_pending`/`try-except-mark_done/mark_error`, что у двух
существующих уровней). `has_pending` в начале `run()` дополнительно
проверяет `queue.next_pending(session, "category_list")`.

**`requeue_stale_lists`:** расширяется с `page_type == "list"` на
`page_type.in_(["list", "category_list"])` — категорийные списки
устаревают по тому же принципу и с тем же порогом (`STALE_AFTER_DAYS`
= 7), что и обычные списки; отдельная функция не нужна.

## Изменения в `store.py`

- `legal_act_id_for_external_id(session, external_id) -> int | None` —
  поиск уже обработанного акта; возвращает `None`, если акт ещё не
  дошёл до сборщика (используется для решения «пропускать»).
- `get_or_create_category(session, external_id, name) -> Category` —
  поиск по `external_id` (не по имени, в отличие от
  `GovernmentBody`/`ActType`, у которых нет собственного числового
  id); если найдена и имя изменилось — обновляет `name` на текущее
  (самовосстановление при переименовании на сайте).
- `link_legal_act_category(session, legal_act_id, category_id, now)` —
  идемпотентная вставка в `legal_act_categories` (не создаёт
  дубликат, если связь уже есть).

## Миграция

Одна новая Alembic-ревизия (`0004`) поверх `0003_reports.py`:
создаёт `categories` (`unique(external_id)`) и `legal_act_categories`
(`unique(legal_act_id, category_id)`, FK на `legal_acts` и
`categories`).

## Тестирование

- `test_list_page.py`: `parse_category_name` — есть нужный `option`,
  нет нужного `option`, категория отсутствует в разметке вообще.
- `test_store.py`: `legal_act_id_for_external_id` до/после вставки
  акта; `get_or_create_category` — создание, повторный вызов не
  дублирует, обновление имени при расхождении; `link_legal_act_category` —
  создание связи, повторный вызов не дублирует.
- `test_run.py`: обход по категории создаёт связь для уже известного
  акта; обход по категории пропускает карточку неизвестного акта, не
  создавая `LegalAct`; пагинация категорийного списка сохраняет
  `categoryId` и продолжается до `totalPages`; `category_list`
  обрабатывается только после исчерпания очередей `list` и `document`;
  `requeue_stale_lists` переоткрывает устаревшие записи обоих типов
  (`list` и `category_list`).

## Критерии приёмки

1. `db/models.py` содержит `Category` и `LegalActCategory` с полями и
   констрейнтами выше; новая Alembic-ревизия применяется чисто поверх
   `0003`.
2. Обход по категории для уже известного акта создаёт запись связи;
   для неизвестного — не создаёт ни акт, ни связь, и не падает.
3. Пагинация категорийных списков работает по всем разделам
   (`npa`/`kdrp`/`arv`/`withdraw`), включая архивные варианты
   `npa`/`arv`.
4. `category_list` не отбирает приоритет у `list`/`document` —
   обрабатывается только когда обе эти очереди пусты.
5. `requeue_stale_lists` переоткрывает устаревшие `category_list`
   записи наравне с `list`.
6. Полный backend pytest-suite проходит.
