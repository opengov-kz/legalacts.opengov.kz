# Архитектурный дизайн: автоматические проверки качества, группа A (уровень записи)

Дата: 2026-09-23

## Контекст

Продуктовое ТЗ (`docs/superpowers/specs/2026-09-20-analytics-product-requirements.md`,
раздел 22.3 «Автоматические проверки») перечисляет 9 проверок. Из них уже
покрыты уникальность `source_id` (структурно, unique-констрейнты в БД) и
«журнал ошибок и повторная очередь» (`GET /crawl/status` +
`requeue_stale_errors`, сделано 2026-09-23 тем же днём). `response time`
явно вне v1 (см. критерии приёмки). Остаются 6 проверок; три из них —
предмет этого дизайна («группа A»), поскольку они работают на уровне
одной записи `LegalAct` в момент её сохранения и естественно встраиваются
в уже существующий `store.upsert_legal_act`:

- «валидность URL и дат»;
- «окончание обсуждения не раньше начала без фиксации ошибки»;
- «счетчики не заменяются `null` или наоборот без события качества».

Оставшиеся три проверки (резкое падение числа объектов; новые
статусы/типы/категории/HTML-структуры; сравнение `comments_total`
источника с фактически собранным числом комментариев) — «группа B»,
агрегатные проверки по всему датасету, требуют отдельного механизма и
отдельного дизайна (не в этой итерации).

Формулировки ТЗ («не заменяются... **без события качества**»,
«...не раньше начала **без фиксации ошибки**») означают: обнаруженная
аномалия не блокирует сохранение записи — акт сохраняется как обычно,
рядом фиксируется факт аномалии.

## Схема таблицы

### `quality_events` (новая)

```text
id                PK (внутренний)
legal_act_id      FK -> legal_acts, not null
event_type        String, not null   -- "invalid_url" | "invalid_date" | "end_before_start" | "counter_null_flip"
field_name        String, not null   -- "url" | "created_date" | "discussion_end_date" | "comments_total" | "likes_count" | "dislikes_count"
detail            Text                -- человекочитаемое описание (напр. "42 -> NULL")
detected_at       DateTime(timezone=True), not null   -- наши часы, UTC
```

Без уникального констрейнта и без апсерта: каждое обнаружение — отдельная
вставка (лог, а не текущее состояние). Это позволяет увидеть, стабильна
проблема при повторных обходах одного акта или была разовой. Без
экспонирования через API v1 в этой итерации (тот же подход, что уже
применён к `DocumentVersion`/`Report`/`Category`) — только сбор в БД.

## Три проверки

Все три реализуются внутри `store.upsert_legal_act`, где уже есть и
старое значение (`existing`), и новое (`values`/`fields`), и после
`session.flush()` — `legal_act.id` для FK.

### 1. `invalid_url`

`LegalAct.url` строится самим сборщиком (`urljoin(BASE_URL, href)`), но
проверка — защита от регрессии, если когда-нибудь `href` окажется
пустым/битым и `urljoin` вернёт мусор. Условие события: `urlsplit(url)`
не даёт непустых `scheme` и `netloc`, либо URL не начинается с
`BASE_URL`.

### 2. `invalid_date` и `end_before_start`

`created_date`/`discussion_end_date` хранятся как сырые строки источника
в формате `DD/MM/YYYY` (подтверждено фикстурой: `"Дата создания:</b>
09/09/2026"`). Новая вспомогательная функция `_parse_source_date(raw) ->
date | None` (`datetime.strptime(raw, "%d/%m/%Y").date()`, `None` при
`ValueError`/пустом значении).

- `invalid_date`: поле непустое, но не парсится этим форматом — по
  отдельному событию на каждое из двух полей, если оно не проходит.
- `end_before_start`: оба поля непустые и оба распарсились, но
  `discussion_end_date_parsed < created_date_parsed` — одно событие.
  Если хотя бы одно поле не распарсилось, эта проверка не выполняется
  (уже покрыто событием `invalid_date` для этого поля).

### 3. `counter_null_flip`

Для каждого из `comments_total`, `likes_count`, `dislikes_count`:
сравнить `getattr(existing, field)` (значение до обновления) с
`values[field]` (новое значение). Событие, если ровно одно из двух —
`None`, а другое нет (в любую сторону — ТЗ буквально требует «или
наоборот»). Если записи `existing` ещё не было (первое сохранение акта)
— сравнивать не с чем, событие не создаётся.

## Изменения в `store.py`

Новая функция `_record_quality_events(session, legal_act_id, existing,
values, now)`, вызывается из `upsert_legal_act` после определения
`legal_act` (чтобы иметь `legal_act.id`), но до `session.commit()` в
конце функции — события коммитятся вместе с самим upsert'ом, одной
транзакцией.

```text
события = []
если invalid_url(values["url"]): события.append(("invalid_url", "url", ...))
для поля created_date, discussion_end_date:
    если invalid_date(поле): события.append(("invalid_date", поле, ...))
если оба поля валидны и end < start: события.append(("end_before_start", "discussion_end_date", ...))
для поля comments_total, likes_count, dislikes_count:
    если null_flip(existing, поле): события.append(("counter_null_flip", поле, ...))
для каждого события: session.add(QualityEvent(legal_act_id=..., event_type=..., field_name=..., detail=..., detected_at=now))
```

## Миграция

Одна новая Alembic-ревизия (`0006`) поверх `0005_crawl_queue_consecutive_errors.py`:
создаёт `quality_events` с FK на `legal_acts`.

## Тестирование

- `test_store.py`: по одному тесту на каждый из 4 `event_type` — валидный
  URL не создаёт событие / битый создаёт; валидная дата не создаёт /
  невалидная создаёт (для обоих полей); конец раньше начала создаёт
  `end_before_start`, конец после начала — нет; флип `42 -> None`
  создаёт событие, `None -> 42` тоже создаёт, `42 -> 43` (оба не-`None`)
  — нет; первое сохранение акта (`existing is None`) не создаёт событий
  по счётчикам.
- `test_db.py`: таблица `quality_events` создаётся, ожидаемые колонки.

## Критерии приёмки

1. `db/models.py` содержит `QualityEvent` с полями и констрейнтами выше;
   новая Alembic-ревизия применяется чисто поверх `0005`.
2. `upsert_legal_act` создаёт события для всех 4 сценариев (битый URL,
   невалидная дата, конец раньше начала, флип счётчика в любую
   сторону), не блокируя само сохранение акта.
3. Первое сохранение акта (нет `existing`) не создаёт ложных событий по
   счётчикам.
4. Полный backend pytest-suite проходит.
