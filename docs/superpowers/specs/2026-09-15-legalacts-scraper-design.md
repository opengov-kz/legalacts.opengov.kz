# Дизайн: парсер портала legalacts.egov.kz

Дата: 2026-09-15
Статус: одобрен, готов к планированию реализации

## 1. Назначение и охват

**Цель:** собрать архив нормативных правовых актов (НПА) с портала
`legalacts.egov.kz` — карточки документов и, в приоритете, обсуждения
с комментариями пользователей — в локальную SQLite-базу для
последующего анализа.

**Охват (весь сайт):**
- Разделы: НПА (`/list`, все статусы — на рассмотрении, на публичном
  обсуждении, архив), КДРП (`/application/kdrpcp`), АРВ (`/Arvlist`),
  отозванные НПА (`/application/withdraw`).
- Обе языковые версии контента: русская и казахская.
- Для каждой страницы сохраняется как извлечённая структура (в
  SQLite), так и сырой HTML — чтобы можно было допарсить новые поля
  позже без повторного обращения к сайту.

**Режим работы:** периодически перезапускаемый скрипт. При каждом
запуске он:
1. Докачивает новые документы (те, что появились в списках с прошлого
   запуска).
2. Перепроверяет ранее собранные документы на появление новых
   комментариев (по истечении настраиваемого интервала с последней
   проверки).
3. Продолжает работу с места, где остановился предыдущий (возможно,
   прерванный) запуск — за счёт состояния очереди обхода в SQLite.

## 2. Модель данных (SQLite)

### `documents`
Карточки актов/проектов (НПА, КДРП, АРВ, отозванные).

| Поле | Назначение |
|---|---|
| `id` | PK |
| `url` | канонический URL карточки |
| `external_id` | id документа на портале |
| `section` | `npa` / `kdrp` / `arv` / `withdraw` |
| `title_ru`, `title_kk` | заголовок на обоих языках |
| `status` | статус (на рассмотрении / на обсуждении / архив / отозван) |
| `doc_type` | закон / приказ / постановление / концепция и т.д. |
| `category_id`, `government_id`, `region_id` | FK на справочники |
| `published_date`, `discussion_start`, `discussion_end` | даты |
| `raw_html_ru`, `raw_html_kk` | сырой HTML карточки на обоих языках |
| `first_seen_at`, `last_checked_at` | служебные метки для докачки |

### `comments`
Комментарии/замечания к документу.

| Поле | Назначение |
|---|---|
| `id` | PK |
| `document_id` | FK → `documents` |
| `external_comment_id` | id комментария на портале |
| `parent_comment_id` | для веток-ответов (nullable) |
| `author_name` | автор |
| `body_ru`, `body_kk` | текст на обоих языках, если доступен |
| `article_ref` | к какому пункту/статье документа относится (если есть) |
| `created_at` | дата комментария |
| `votes_up`, `votes_down` | голосование, если есть |
| `first_seen_at` | когда впервые собран |

### `categories`, `government_bodies`, `regions`
Справочники фильтров: `id, name_ru, name_kk, parent_id`. Иерархия
важна для гос. органов (центральные ↔ региональные) и регионов
(области ↔ районы).

### `crawl_queue`
Очередь и состояние обхода — основа резюмируемости и докачки.

| Поле | Назначение |
|---|---|
| `url` | адрес страницы |
| `page_type` | `list` / `document` / `comments_page` |
| `status` | `pending` / `done` / `error` |
| `attempts` | счётчик попыток |
| `last_error` | текст последней ошибки |
| `discovered_at`, `processed_at` | служебные метки |

При повторном запуске: (а) новые URL из списков добавляются как
`pending`; (б) документы с `last_checked_at` старше настраиваемого
порога переводятся обратно в `pending` для проверки новых
комментариев.

## 3. Обход, вежливость, обработка ошибок

**Порядок обхода:** сначала списочные страницы (`/list`, `/Arvlist`,
`/application/kdrpcp`, `/application/withdraw`) со всеми фильтрами по
статусу — извлекаются ссылки на карточки документов и кладутся в
`crawl_queue`. Затем обрабатывается очередь: для каждого документа —
карточка на обоих языках + комментарии (встроены в HTML карточки или
подгружаются отдельно — уточняется в ходе реализации).

**Вежливость:**
- Один запрос за раз (без конкурентности).
- Задержка между запросами ~0.5–1 сек с небольшим случайным джиттером.
- Постоянный user-agent, уважение к `robots.txt`.

**Обработка ошибок:**
- Сетевая ошибка / 5xx → retry с экспоненциальной паузой, до N
  попыток; при исчерпании — `status=error` + `last_error`, обход
  продолжается дальше по очереди.
- 404 → помечается `done` с пометкой "не найдено", не ретраится.
- Запись результата (сырой HTML + распарсенные поля) в SQLite
  выполняется в одной транзакции одновременно с переводом URL в
  `done` — чтобы прерывание скрипта не оставляло половинчатых записей.

## 4. Технологии, структура проекта, тестирование

**Стек:** Python 3.8, `requests`, `beautifulsoup4` (+ `lxml`),
стандартный `sqlite3`. Зависимости — `requirements.txt`, окружение —
`venv`.

**Структура проекта:**

```
legalacts.opengov.kz/
├── scraper/
│   ├── __init__.py
│   ├── db.py            # схема SQLite, миграции, работа с crawl_queue
│   ├── fetch.py         # HTTP-клиент: задержки, retry, user-agent
│   ├── parsers/
│   │   ├── list_page.py     # парсинг списков → ссылки на документы
│   │   ├── document_page.py # парсинг карточки документа
│   │   └── comments.py      # парсинг комментариев/веток
│   └── run.py            # точка входа: обход очереди
├── tests/
│   ├── fixtures/          # сохранённые реальные HTML-страницы для тестов
│   └── test_parsers.py
├── requirements.txt
└── legalacts.db            # SQLite (в .gitignore)
```

**Тестирование:** бить по живому сайту в автоматических тестах нельзя
(нарушает вежливость и нестабильно). Парсеры тестируются на заранее
сохранённых HTML-фикстурах (реальные страницы, сохранённые на старте
разработки) — проверяется корректное извлечение полей документа и
комментариев. Отдельный ручной прогон на 1–2 живых страницах — как
sanity-check перед полным запуском.

## Открытые вопросы для этапа реализации

Эти детали не влияют на архитектуру, но требуют проверки на живом
сайте в начале реализации:
- Точная структура пагинации списков (`page` в query, кнопки, offset).
- Загружаются ли комментарии внутри HTML карточки документа или через
  отдельный запрос/AJAX-эндпоинт.
- Точные значения query-параметров статуса/типа для полного перебора
  фильтров без дублирования документов.

## Уточнения по итогам разведки реальной разметки (2026-09-15)

При переходе к написанию плана реализации сайт был обследован напрямую
(`curl` по реальным страницам `/list`, `/Arvlist`,
`/application/withdraw`, `/application/kdrpcp`, `/npa/view?id=...`).
Часть решений раздела 2 уточнена по факту:

- **Пагинация:** `?page=N` — обычный GET-параметр (SSR, без AJAX),
  общее число страниц зашито в `<script>` на первой странице списка
  (`totalPages: N`), 5 документов на странице.
- **Разделы используют один и тот же шаблон списка:** `/Arvlist` и
  `/application/withdraw` рендерят те же блоки `.contentlist`, что и
  `/list`. `/application/kdrpcp` — это редирект на
  `/list?types[0]=7001&types[1]=7002`, т.е. КДРП — просто НПА,
  отфильтрованные по `types[]`, отдельный парсер не нужен.
- **Язык:** переключение ru/kk — не параметр URL, а cookie
  `egovLang=ru|kk` (домен `.egov.kz`), выставляется одним GET-запросом
  на `/application/changelang?lang=kk&location=...`. Для обеих версий
  нужны две `requests.Session` с разными cookie.
- **Комментарии не имеют votes_up/votes_down.** У каждого комментария
  вместо этого статус «Принято» / «Не принято» (иконка
  `fa-check-square` / `fa-times-circle`). Официальный ответ ведомства —
  это вложенный `div.media` внутри комментария, т.е. по факту дочерний
  комментарий (`parent_comment_id`), а не отдельная сущность.
- **Категория и орган-разработчик не связаны с документом как id.**
  Категория вообще не отображается на карточке/странице документа.
  Орган-разработчик показан только как **текст** (например,
  «Министерство труда и социальной защиты населения РК»), без id.
  Полная привязка к `categoryId`/`governmentId` потребовала бы
  отдельного обхода ~500+ фильтров и сопоставления — решено это не
  делать в MVP.

**Решение по объёму MVP:** справочники `categories`,
`government_bodies`, `regions` и колонки `category_id`,
`government_id`, `region_id` на `documents` из раздела 2 **исключены
из v1**. Орган-разработчик хранится как обычный текст на
`documents.government_body`. Голосование комментариев (`votes_up`,
`votes_down`) заменено на `status` (принято/не принято/NULL).
Полная нормализация категорий/органов власти — кандидат на отдельную
последующую итерацию, не блокирует сбор архива обсуждений и
комментариев, который является приоритетом.

- **Текст комментариев не переводится.** Сравнение одного и того же
  документа в ru- и kk-версиях показало, что текст пользовательских
  комментариев идентичен в обеих версиях — переводится только сам
  текст НПА (заголовок, содержание) и интерфейс. Поэтому в `comments`
  вместо `body_ru`/`body_kk` — одно поле `body`. kk-версия документа
  запрашивается только ради `title_kk`/`raw_html_kk`, комментарии
  парсятся один раз из ru-версии.

- **`robots.txt` запрещает именно то, что нужно собрать.** Проверка
  `https://legalacts.egov.kz/robots.txt` показала `Disallow: /npa/view`
  (единственный маршрут карточки документа с комментариями) и
  `Disallow: /application` (включая переключение языка
  `/application/changelang` и `/application/withdraw`). Списки
  (`/list`, `/Arvlist`) не запрещены.

  **Осознанное решение:** запрет для `/npa/view` и `/application`
  игнорируется — без этого сбор архива обсуждений с комментариями
  (приоритет проекта) невозможен в принципе. Правило вежливости по
  скорости запросов (раздел 3) остаётся в силе без изменений —
  запрет игнорируется точечно только для этих двух путей, а не как
  общий отказ от уважения к `robots.txt`.

## Уточнения по итогам живой проверки источника (2026-09-21)

В рамках Этапа 1 (`docs/superpowers/specs/2026-09-20-analytics-product-requirements.md`,
раздел 27) сайт повторно обследован напрямую (`curl`/WebFetch по
`/robots.txt`, `/list`, `/Arvlist`, `/list?types[0]=...`,
`/application/withdraw`, живым карточкам `/npa/view?id=...` и
`/npa/viewArvConclusion?id=...`). Часть решений уточнена, обнаружены
два расхождения текущей реализации (`backend/scraper/`) с описанным
выше поведением:

- **Полный список `Disallow` в `robots.txt` шире, чем зафиксировано
  выше.** Помимо `/npa/view` и `/application`, запрещены также
  `/report`, `/legalact/`, `/filtercomments/`, `/public`,
  `/subscriptioncontroller/` (плюс служебные пути `/admin/`,
  `/security/`, `/captcha/` и т.п., скрейпера не касаются). Текущий
  код не обращается ни к одному из новых путей, поэтому решение
  раздела выше пока не требует расширения — но при реализации
  будущих этапов (отчёты — раздел 11.3 продуктового ТЗ; неосновные
  вкладки комментариев — см. ниже) потребуется то же осознанное
  решение владельца продукта, что уже принято для `/npa/view` и
  `/application`.

- **⚠️ Раздел АРВ (`arv`) не использует `/npa/view?id=...`.** Карточки
  `/Arvlist` ссылаются на **`/npa/viewArvConclusion?id=...`** — другой
  шаблон страницы. Живая проверка показала, что этот шаблон **не
  содержит класс `.view-npa`** вообще (заголовок — обычный `<h2>` вне
  `.view-npa`, подписи `Тип НПА:`/`Дата создания:` лежат в простом
  `<div>`). `backend/scraper/parsers/document_page.py` целиком
  построен на селекторах `.view-npa h2` / `.view-npa small b`, а
  `parse_comments` — на `.blog-info i[title="Всего комментариев"]` и
  `.main-comments`, которых на этом шаблоне тоже нет. **Практический
  эффект:** для каждого документа раздела `arv` в БД сейчас `title_ru`,
  `title_kk`, `status`, `doc_type`, `created_date`,
  `discussion_end_date` сохраняются как `NULL`, `comments_total` = 0,
  список комментариев всегда пуст. Реально заполняются только
  `government_body`, `likes_count`, `dislikes_count`, `url`,
  `external_id`, `section`. Раздел `withdraw`
  (`/application/withdraw`) на момент проверки пуст на сайте («Нет
  данных») — его шаблон карточки живьём проверить не удалось.
  **Статус: исправлено (2026-09-21).** `document_page.py` расширен
  объединёнными селекторами (`.view-npa h2, .blog-item h2` и т.д.) —
  на шаблоне `/npa/view` класс `blog-item` висит на пустом `<br>`, так
  что конфликта между шаблонами нет. `parse_comments` уже корректно
  возвращал `[]` при отсутствии `.main-comments` — падений не было, это
  не баг, а особенность шаблона (у карточек `arv` нет вкладок
  комментариев). Тесты: `test_parse_document_page_reads_arv_conclusion_template`,
  `test_parse_comments_returns_empty_list_for_arv_conclusion_template`,
  фикстура `backend/tests/fixtures/document_arv_conclusion.html`.

- **⚠️ Гонка языка при холодном старте `Fetcher`.** Без cookie
  `egovLang` сайт по умолчанию отдаёт **казахскую** версию (не
  русскую, как можно было бы предположить). `backend/scraper/run.py`
  создаёт новый `Fetcher` (новую `requests.Session` без cookie) на
  каждый вызов `run()`, а `set_language("ru")` вызывается только
  внутри `process_document_entry` — уже после того, как ru-запрос
  первого документа цикла успевает уйти без переключения языка.
  Поскольку `worker/loop.py` вызывает `run()` в бесконечном цикле,
  это повторяется на каждой итерации: первый документ каждого цикла
  сохраняет казахский HTML под видом `raw_html_ru`/`title_ru`, а
  `doc_type`/`created_date`/`discussion_end_date` парсятся как `NULL`
  (лейблы `LABEL_MAP` — русские, ищутся в казахском тексте).
  **Статус: исправлено (2026-09-21).** `run()` теперь вызывает
  `fetcher.set_language("ru")` сразу после создания `Fetcher`, до
  цикла обработки очереди. Тест:
  `test_run_switches_to_russian_before_first_document_fetch`.

- **Разделы экспертного участия (раздел 6.4 продуктового ТЗ)
  подтверждены живьём.** На каждой карточке `/npa/view` есть до 8
  вкладок комментариев: «Пікір»/«Комментарий» (дефолтная,
  `typeComment=6`, это то, что уже парсит `parse_comments`), «Атамекен»
  ҰҚП (`3`), Қоғамдық және сараптамалық кеңестер (`1`),
  антикоррупционная экспертиза (`8`), научно-правовая экспертиза (`9`),
  научно-экономическая экспертиза (`10`), ЗҚАИ и члены ВАК (`7`),
  аккредитованные НКО (`4`). Переключение вкладки — обычная навигация
  `/npa/view?id=<id>&typeComment=<N>` (тот же уже принятый риск
  `robots.txt`, никакого отдельного AJAX-эндпоинта вроде
  `/filtercomments/` не требуется), контейнер результата — тот же
  `.main-comments`, что уже разбирает `parse_comments`. Расширение
  сборщика на эти вкладки технически несложно, но пока не сделано.

- **Поля, ранее отнесённые к "target/v2", подтверждены как
  существующие в разметке `/npa/view`** (но сознательно не собираются
  в v1 — см. `docs/superpowers/specs/2026-09-20-analytics-product-requirements.md`,
  раздел 6.5): «Жоба нұсқасы»/«Версия проекта», время начала/окончания
  онлайн-обсуждения, приложенные файлы (`ul.conceptFiles`,
  `/application/downloadconceptfile?id=...`). Расхождений со спекой
  здесь нет.
